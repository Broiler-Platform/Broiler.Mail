# M4 — International received-attachment filenames

Five completed interoperability items extend the existing bounded receive/save workflow:

1. **Single extended parameters:** decode `filename*` and Content-Type `name*` percent-encoded octets using the declared charset. A valid extended value takes precedence over its ordinary fallback; disposition filename takes precedence over Content-Type name. UTF-8 and installed .NET/code-page encodings use exception fallback, so invalid bytes never silently become replacement characters. Language metadata is consumed without changing UI language. Unspecified charset is supported for ASCII octets only; no non-ASCII charset is guessed. A plus sign remains a plus sign.
2. **Continuations:** assemble numbered segments in numeric order regardless of header ordering, supporting plain, encoded and mixed segments. Bytes are combined before character decoding, including UTF-8 characters split between segments. Sequence starts at zero, is contiguous, and has no leading-zero indexes. At most 32 segments and 16 KiB decoded extended-name bytes are accepted.
3. **Quoted/legacy interoperability:** quoted semicolons and escaped quote/backslash characters are parsed correctly. Ordinary legacy RFC2047 names remain supported. Extended names are not subsequently treated as encoded words, avoiding a second interpretation of a decoded name. Named text attachments remain excluded from the main reader body; inline-image resource behavior is preserved.
4. **Failure and path safeguards:** duplicate parameter names/indexes, conflicting single/continued forms, invalid percent escapes, missing charset delimiters, unavailable encodings and invalid charset bytes reject the entire extraction inventory. Header parsing is bounded to 64 KiB and 256 parameters. Ordinary preview remains tolerant of malformed names; an extended-name marker still prevents named text from becoming the body. Decoded paths, control/format characters and unsafe filename characters pass through the existing sanitizer, 120-unit display-name cap, unique prefix and non-overwriting local save.
5. **Acceptance:** tests cover international charsets, mixed/reordered continuations, quoted syntax, name-only text classification, ambiguous/malformed/oversized input, single decoding and exact saved bytes. Published NativeAOT application smoke uses a continued UTF-8 name; the production loopback TLS/STARTTLS probe uses a Latin-1 extended name and verifies exact attachment bytes without another IMAP command.

These rules follow [RFC2231 sections 3–4.1](https://www.rfc-editor.org/rfc/rfc2231.html), with explicit local resource limits and conservative rejection policies. Basic and extended forms may coexist; invalid extended values do not silently fall back during extraction. In ordinary preview, malformed values retain a basic fallback or a generic attachment name. This change does not alter source bytes, hashes, profile schema, backup boundaries, quotas or sending.

The existing whole-original **2 MiB**, **32 attachment** limit still applies. Files stay under the profile attachment-export directory and are never opened automatically. Compose/send attachments, streaming/large-message support, export browsing/import, destination dialogs, broader provider/accessibility/other-target acceptance and renderer containment remain open. M0–M4 are not collectively complete.
