# M4 — Bounded received-attachment extraction

Current Windows x64 behavior supports originals up to 12 MiB. **Download original .eml** streams the bytes to a temporary file with byte progress, then publishes the file and receipt after the UID, size and server response match. Canceling before publication discards the temporary file. Open the verified original's attachment list to save a part. Extraction uses a bounded in-memory MIME parser. The original 2 MiB implementation and evidence are recorded below.

Five completed items extend the current original-source export without another server request:

1. **Inventory:** parse attachment leaves from the verified saved `.eml`, retaining full account/folder/UIDVALIDITY/UID identity, source SHA-256, leaf ordinal, safe filename, media type, decoded length and SHA-256. Attached text/HTML does not become the reader body. Explicit image attachments do not become embedded resources. CID/location inline resources are omitted; legacy filename-only image resources remain renderable and may also be listed as attachments.
2. **Integrity:** strict attachment base64 and quoted-printable decoding rejects malformed input and unsupported transfer encodings. Binary/7bit/8bit retain bytes. Delimiters must occupy MIME boundary lines. Incomplete structures, unsupported attached multipart containers and exceeded bounds reject the entire inventory. Normal body preview retains its tolerant decoding.
3. **Local saving:** re-read and verify the source receipt, re-parse and match the entire selected descriptor before writing. Generated filenames strip path/control characters, cap the displayed filename at 120 UTF-16 units, and receive a unique prefix. Staged create-new writes are flushed before non-overwriting promotion. Independent locking enforces 64 files/128 MiB; no automatic eviction or opening occurs.
4. **Reader controls:** after explicitly exporting an original, choose “Read attachments from saved .eml”, select a part, then “Save selected attachment”. No automatic inventory/save occurs. Cancel, replacement, account/message changes and disposal reject stale results. The selectable read-only receipt shows path, bytes and checksum. A cancellation racing a committed save can leave its file on disk; the UI explains this.
5. **Acceptance and lifecycle:** regression coverage includes exact binary/QP bytes, invalid encodings, boundary collisions, header/part limits, safe filenames, changed receipts/source, quota races, cancellation and stale UI results at 100%/200%. Published application smoke checks extraction without another receiver call, unchanged cached body, cache-clear retention and backup exclusion. The NativeAOT loopback TLS/STARTTLS probe checks production receive/export/extraction bytes without another IMAP command.

The whole original must fit **2 MiB**, including headers and encoded attachments. Inventory permits **32 attachments**, **256 leaf parts**, nesting **32**, and in strict extraction mode **64 KiB headers and 256 parsed headers per entity**. Basic `filename`/Content-Type `name` parameters and legacy RFC2047 names are supported. [RFC2231 extended/continued names](m4-attachment-filenames.md) are now also supported with bounded strict extraction validation. This is bounded in-memory extraction, without streaming or resume.

Files live in `<profile>/attachment-exports`, independently of `<profile>/source-exports`. Cache cleanup retains both. Verified profile backup/restore excludes both: back these exported files up separately. Each save creates a new file and consumes quota, including zero-byte attachments; unfinished partial files also count. No profile schema migration or retained-original cache is added.

The reader uses its active verified source-export receipt. The [saved-original picker](m4-saved-originals.md) now restores cataloged receipts for the same message after restart. General export browsing, arbitrary `.eml` import/open, user-chosen destination dialogs, compose/send attachments, large-message handling, broader provider/accessibility/other-target acceptance and renderer containment remain open. The broad attachment round-trip roadmap item stays unchecked.
